## The problem

PC players collect games far faster than they can play them. A Steam library tells you what you own, not where you are: which ones you started, which you dropped after two hours, which have been waiting for a year.

That is where Arcadium comes from. It is a platform that looks like Steam but serves a different purpose: it is not for buying games, it is for keeping order among the ones you already have.

## How it works

The system is split into five layers and each one does a single thing. The Steam dataset enters once through an ETL pipeline written in Python. The PostgreSQL database becomes the source of truth. A Spring Boot backend exposes everything through JWT-protected REST endpoints. The Next.js frontend consumes that API and draws the interface.

The most important boundary is also the most mundane to honour: the frontend does not know the database. It has no credentials, no connection, and could not reach it even if it wanted to. Every piece of data goes through a documented endpoint.

## From dataset to database

The part that took the most work was not writing code, but understanding what was actually in the source file.

The header merged two columns into one, which shifted every value up to the middle of the row by one position. The AppID, which identifies a game on Steam, did not appear in the data at all: it was reconstructed from the `/apps/<AppID>/` path present in the image URLs. Sixty-six games appeared with multiple snapshots of the same title, and for each one we had to decide which snapshot to keep.

What remains is 122,479 games with entirely distinct AppIDs, plus twenty-two rows with a null identifier: cases that could not be determined with certainty, and where inventing a number would have been worse than admitting the gap.

The load runs in roughly 65 seconds and can be re-run as often as you like. That is not a promise: two consecutive runs leave all eleven affected tables with identical counts, from 122,479 games up to 1,178,560 game-to-tag relationships.

## Security and access

Authentication is stateless: after login the backend issues a JWT that the client attaches to every protected request. Passwords are only stored hashed. There are five public endpoints in total; everything else requires a valid token.

The Steam integration is the most interesting part, because it changed shape during the project. The first version used a server key to read every user's data. The final version flips the model: the user generates their own key on Steam's official page and pastes it into their settings, where it is stored encrypted. Syncing is on demand, adds new games with the "never played" state, updates the hours of games already there, and deletes nothing.

## What happened when I rebuilt it

I rebuilt the Docker environment months after delivery, and two things broke immediately.

Flyway refused to start: the database volume still held the history of two migrations that no longer existed in the code. The frontend container, meanwhile, died on every start because the image copied files as root and then switched to an unprivileged user who could no longer write the Next cache.

Neither is a flaw in the application logic, and that is exactly the point: a project works as long as the environment underneath tells the same story as the code. When the two versions diverge, the best thing that can happen is for something to stop loudly, instead of carrying on and pretending everything is fine.
